# Feature Specification: パステルテーマ適用（MUI不使用）

**Feature Branch**: `002-mui-pastel-theme`  
**Created**: 2026-02-26  
**Status**: Draft  
**Input**: User description: "Material UI（MUI）は使用しない」「全体テーマはパステルカラー基調"

## Clarifications

### Session 2026-02-26

- Q: エラー/警告などの重要状態の配色はパステルに寄せますか？ → A: 高コントラスト最優先（パステル基調でも、エラー色は同等に目立つ高コントラスト色を許容）
- Q: UIコンポーネント統一で Material UI（MUI）を使用しますか？ → A: 使用しない
- Q: 重要テキストのコントラスト基準は設けますか？ → A: WCAG AA を満たす（目安: 通常文字 4.5:1、太字/大文字 3:1）
- Q: 「主要画面」の対象範囲はどこまでですか？ → A: フロントエンドの全ページ（将来増えるページも含め対象）
- Q: UIコンポーネントの統一は何で実現しますか？ → A: Tailwindで統一（追加のUIライブラリは導入しない）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - パステル基調のUIで迷わず操作できる (Priority: P1)

学習者として、画面全体がパステルカラー基調で統一され、主要操作（追加/一覧確認/削除）が分かりやすいUIで使いたい。そうすることで、見た目の違和感や操作の迷いが減り、学習の継続に集中できる。

**Why this priority**: UIの統一感と見やすさは、毎日触る運用での満足度と継続率に直結するため。

**Independent Test**: 一覧画面を開き、学習項目を1件追加し、一覧に表示され、削除できることを確認できる。あわせて、ボタン/入力/表/見出しがパステル基調で統一されていることを目視確認できる。

**Manual Verification Checklist**:

- [ ] 画面全体（背景/文字色）がパステル基調で統一されている
- [ ] 見出し/補助テキスト/セクション（カード）が統一された余白・枠線で表示される
- [ ] 入力（タイトル/内容/タグ）が統一された見た目で、フォーカスが分かる
- [ ] 追加に成功すると、一覧に反映される
- [ ] 一覧のタグが統一されたバッジ表現で表示される
- [ ] 一覧から削除でき、削除中はボタンが無効化され状態が分かる
- [ ] 取得/追加/削除の失敗表示が通常表示と区別できる（高コントラスト）

**Acceptance Scenarios**:

1. **Given** アプリのトップ画面を開いている, **When** 画面を閲覧する, **Then** 主要な領域（見出し/入力/ボタン/一覧）が同一のテーマに沿った配色と余白で表示される
2. **Given** 学習項目の追加フォームが表示されている, **When** タイトル等を入力して追加する, **Then** 追加ボタンや入力欄の見た目がテーマに沿っており、追加後に一覧が更新される

---

### User Story 2 - 端末サイズが変わっても視認性を維持できる (Priority: P2)

学習者として、スマホ/タブレット/PC など画面幅が変わっても、文字が読めて操作ができる状態で使いたい。

**Why this priority**: 使用環境が変わるとUI崩れが起きやすく、継続利用を阻害するため。

**Independent Test**: 主要画面をスマホ幅・タブレット幅・PC幅で表示し、入力と一覧の操作が行えることを確認できる。

**Manual Verification Checklist**:

- [ ] スマホ幅でもフォームの入力と送信ができる（はみ出し/操作不能がない）
- [ ] スマホ幅でも一覧が操作不能にならない（横スクロールでき、削除ボタンが押せる）
- [ ] タブレット幅/PC幅でも情報が判別でき、詰まりすぎない

**Acceptance Scenarios**:

1. **Given** 主要画面をスマホ幅で表示している, **When** 入力と一覧を操作する, **Then** レイアウト崩れにより操作不能にならない
2. **Given** 主要画面をPC幅で表示している, **When** 入力と一覧を操作する, **Then** 情報が詰まりすぎず、見出し/フォーム/一覧が判別できる

---

### Edge Cases

- パステル基調であっても、重要な文言（エラー/警告/期限切れ等）は高コントラストで表示され、背景に埋もれずユーザーが状態を判別できる（エラー色は同等に目立つ高コントラスト色を許容）
- パステル配色の調整により、ボタンラベル/入力ラベル/エラーメッセージ等のコントラストが不足しない（WCAG AA の目安: 通常文字 4.5:1、太字/大文字 3:1）
- 端末やブラウザの表示差（色味/フォント/拡大率）により見え方が変わっても、主要操作が判別できる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST フロントエンドの全ページで利用する主要UIコンポーネント（ボタン/入力/表/見出し/通知など）を統一する（Material UI（MUI）は使用せず、Tailwindで統一する）
- **FR-002**: System MUST 全体テーマをパステルカラー基調として定義し、フロントエンドの全ページの要素（背景/見出し/ボタン/入力/表）に一貫して適用する
- **FR-003**: System MUST フロントエンドの全ページがスマホ/タブレット/PC の画面幅で操作できる状態を維持する
- **FR-004**: System MUST フロントエンドの全ページで、エラー表示や重要な状態（例: 期限切れ等）が、テーマ適用後も高コントラストで判別できるように表示する（エラー色は同等に目立つ高コントラスト色を許容し、重要テキストはWCAG AAの目安を満たす）
- **FR-005**: System MUST テーマ変更により既存の主要機能（学習項目の追加/一覧表示/削除等）の挙動を変更しない

### Acceptance Criteria for Functional Requirements

- **FR-001**: フロントエンドの全ページで使用されるボタン/入力/表などが同一のコンポーネント体系により表示され、見た目の不統一が目視で発生しない
- **FR-002**: フロントエンドの全ページで、背景・見出し・主要アクション（ボタン）・主要フォーム要素などがパステル基調で統一されている
- **FR-003**: スマホ幅/タブレット幅/PC幅で、主要操作が行え、横スクロールやはみ出しで操作不能にならない
- **FR-004**: エラー時にエラーメッセージが表示され、通常時と区別できる。かつ、重要テキスト（ボタンラベル/入力ラベル/エラーメッセージ等）はWCAG AAの目安（通常文字 4.5:1、太字/大文字 3:1）を満たす
- **FR-005**: テーマ変更前後で、学習項目の追加→一覧反映→削除が同様に実行できる

### Scope

- フロントエンドの全ページ（将来増えるページも含む）に対して、主要UIコンポーネントの統一（Tailwind）とパステルテーマ適用を行う

### Out of Scope

- 新しい画面や機能の追加（テーマ適用のために必要な最小限の表示調整を除く）
- ダークモードの提供
- 外部UIコンポーネントライブラリの導入（例: Material UI（MUI）など）
- 端末間同期や認証など、UIテーマと無関係な機能追加

### Assumptions

- 「パステルカラー基調」は、淡い色合いをベースにしつつ、主要操作と重要な状態が判別できる配色である（重要テキストはWCAG AAの目安: 通常文字 4.5:1、太字/大文字 3:1）
- Material UI（MUI）は使用しない
- UIコンポーネントの統一はTailwindで実現する（追加のUIライブラリは導入しない）

### Dependencies

- 既存画面がレンダリング可能であり、テーマ適用後も主要操作（追加/一覧/削除）が実行できること

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 初見ユーザーがトップ画面で学習項目を1件追加し、一覧で確認するまでを1分以内に完了できる
- **SC-002**: スマホ幅/タブレット幅/PC幅の3パターンで、主要操作（追加/一覧確認/削除）がそれぞれ完了できる
- **SC-003**: 主要画面で「エラー表示」と「通常表示」をユーザーが区別でき、誤操作（何をすれば良いか分からない）を発生させない
